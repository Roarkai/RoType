# 0.0.1 首次安装后的菜单错位复现

## 已观察到的失败

用户重新安装 0.0.1/build 34 后，顶部菜单没有洛克条目，勾选豆包，却显示洛克提供的命令区。已安装包版本、签名、TIS 名称与 bundle/mode ID 正确。

`bash scripts/test-installed-input-menu.sh` 在原现场明确失败：

```
TIS 当前输入源: im.roarkai.inputmethod.Luoke.Hans
菜单实际勾选: 豆包输入法
```

系统设置的原生输入法列表已经列出 ABC、豆包、洛克；不能把“系统设置里有条目”当作顶部菜单健康的证据。

## 单变量对照

1. 用公开 TIS API 选择 ABC，再选择洛克；每次运行 RunLoop 等待一秒。API 均返回 0，菜单仍停在 ABC，验收失败。故不只是豆包相关的名称冲突，也不是 CLI 完全没有等待。
2. 在系统设置关闭再开启“在菜单栏显示输入法菜单”，保持原设置不变。重跑仍失败。
3. 在系统设置中只移除洛克输入源条目，再通过“＋ → 简体中文 → 洛克输入法 → 添加”重新加入；不改应用文件、词库、用户配置、ABC 或豆包。重跑验收通过。
4. 再通过真实菜单连续三轮“豆包 → 洛克”切换，每轮等待一秒，API/菜单一致性检查全部通过。

本轮未重启菜单进程、未注销、未重置 HIToolbox 偏好，也没有通过写私有偏好实现添加。曾误截到其他前台窗口的临时图片已删除；后续仅用指定的系统设置窗口 ID 截图。

## 结论与边界

证据定位到程序化启用/选择与原生添加路径之间的差异。`TISEnableInputSource`/`TISSelectInputSource` 成功、甚至真实 controller 接收输入，都不足以证明顶部菜单已正确接纳该源。不能据此断言 Apple 内部究竟是哪一层缓存或通知缺陷。

之前添加 ABC 的恢复只证明过一次现场恢复，未区分缺少 ABC 和原生设置变更触发同步。此次已有 ABC 仍复发，排除了“只要保留 ABC 就永久解决”的说法。

## 开发修正

- 安装器只做注册，不再对首次用户自动 enable/select；升级同样不强制切换。
- 未验证用户的设置主按钮打开原生键盘设置，提供完整添加和从顶部菜单选择的步骤。
- 安装命令夹具先红后绿，约束所有进度状态都不得自动 enable/select。
- 真实菜单一致性脚本仍是必要的安装验收，不以 32 个单元测试、公证或包内 Rime 测试代替。

当前机器已恢复，源码修正尚未重新打包。本次三轮菜单通过不代表新安装流程已在全新环境验收；下一个包必须验证“原生添加 → 顶部选择 → 试打”，不能再次跳过。
